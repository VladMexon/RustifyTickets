# Архитектура

Документ описывает внутреннее устройство проекта: слои, алгоритм классификации,
взаимодействие бэкенда и фронтенда, формат отчёта и известные ограничения.

## Слои

| Слой | Расположение | Отвечает за |
|---|---|---|
| Ядро | `src/lib.rs`, `src/categories.rs`, `src/report.rs` | Чтение xlsx, классификация, запись отчёта, пути конфига |
| CLI | `src/main.rs` | Аргументы командной строки, вывод статистики |
| Бэкенд GUI | `src-tauri/src/main.rs` | Tauri-команды, состояние сессии, диалоги, события |
| Фронтенд | `ui/src/*.ts` | Интерфейс: загрузка, таблица, графики, редактор |

Ключевое правило: **ядро не знает про интерфейс**. Оно принимает путь к файлу и
набор правил, возвращает результат. Всё, что специфично для GUI (диалоги,
состояние между вызовами, пагинация), живёт в `src-tauri`.

Зависимости направлены в одну сторону: `ui` → `src-tauri` → `src` (крейт
`RustifyTickets` подключается как path-зависимость под именем `rustifytickets`).

## Поток данных

```
categories.toml ─┐
                 ▼
  .xlsx ──► classify_file(path, config) ──► ClassificationResult
                                                    │
                        ┌───────────────────────────┴──────────────────┐
                        ▼                                              ▼
              save_report(result, out)                      FileSummary / DataPage
                        │                                              │
                        ▼                                              ▼
                 отчёт .xlsx                                  JSON через IPC → ui
```

1. `classify_file` читает первый лист книги, находит колонку «Описание»,
   классифицирует каждую строку и собирает статистику.
2. CLI сразу вызывает `save_report`; GUI сначала отдаёт сводки в интерфейс,
   а отчёт сохраняет по кнопке (повторно используя закэшированный результат).

## Ядро

### `src/lib.rs`

| Элемент | Назначение |
|---|---|
| `ClassificationResult` | Заголовки, строки с категорией, счётчики по категориям, имя файла |
| `ClassificationResult::total()` | Число строк |
| `AppError` | `Io`, `Xlsx`, `BadWorkbook`, `Config` — с человекочитаемым `Display` |
| `classify_file(path, config)` | Классификация одного xlsx |
| `save_report(result, path)` | Запись отчёта: лист «Данные» + лист «Статистика» |
| `default_config_path()` | Поиск рабочего конфига (см. ниже) |
| `user_config_dir()` | `%APPDATA%\RustifyTickets` или `~/.config/rustifytickets` |
| `write_config(path, contents)` | Запись конфига с созданием родительских папок |

Чтение Excel делает `calamine`, запись — `rust_xlsxwriter`. Если в файле нет
колонки «Описание», возвращается `AppError::BadWorkbook` с понятным текстом, а не
паника.

### `src/categories.rs`

| Элемент | Назначение |
|---|---|
| `CategoriesConfig` | `version` + `categories: Vec<CategoryRule>` |
| `CategoryRule` | `name`, `include`, `exclude`, `weight`, `priority` |
| `from_toml_str` / `from_file` | Разбор и валидация правил |
| `defaults()` | Встроенный стандарт из `include_str!("../categories.toml")` |
| `validate()` | Непустой список, уникальные имена категорий |
| `classify(text)` | Применение правил к одной заявке |
| `UNCLASSIFIED` | «Не классифицировано» |
| `DEFAULT_CATEGORIES_TOML` | Текст стандартного набора, вшитый в бинарь |

### Алгоритм классификации

```
текст → trim → to_lowercase
для каждой категории по порядку объявления:
    если найдено любое слово из exclude → категория пропускается
    score = weight × (число найденных слов из include)
    если score > 0 и (score больше лучшего ИЛИ равен, но priority меньше) → лучшая
вернуть имя лучшей категории либо UNCLASSIFIED
```

Детали, которые важно учитывать:

- **Сопоставление — по подстроке.** `"газоанализ"` найдётся внутри
  `"газоанализаторы"`. Морфологии нет: чтобы покрыть формы, пишите корень слова.
- **Вес умножается на количество совпадений**, а не на длину слова. Категория с
  `weight = 1` и тремя найденными словами даёт 3.
- **Приоритет — только тайбрейкер.** Он сравнивается лишь при равных score.
  По умолчанию `priority = 0`, поэтому без явной расстановки ничьи решает
  порядок объявления категорий.
- **`exclude` сильнее `include`**: достаточно одного совпадения, чтобы категория
  не рассматривалась вовсе.
- Регистр не важен, но `to_lowercase` не сворачивает `ё` в `е` — в правилах
  полезно держать оба варианта написания.

Пример 1: текст «Не идет отпуск топлива по ТРК, колонна не отпускает».

| Категория | Совпавшие слова | Score |
|---|---|---|
| Ошибки КАСУ - ТРК | `трк`, `не идет`, `отпуск топлива`, `колон`, `не отпускает` | 5 |
| Ошибки КАСУ - общее | — | 0 |

Побеждает ТРК: у неё наибольшая сумма, а `exclude` (`отчет`, `отчёт`) в тексте не
встречается.

Пример 2: тот же текст, но добавлено «сформирован отчет».

| Категория | Что произошло | Итог |
|---|---|---|
| Ошибки КАСУ - ТРК | 5 совпадений, но сработал `exclude` (`отчет`) | категория не рассматривается |
| Петроникс - Сменный отчет | совпало `отчет`, `сформировано` | score 2, побеждает |

Так `exclude` перехватывает заявку у категории с формально большим score — это
основной инструмент разрешения конфликтов между категориями.

## Конфигурация

### Формат

```toml
version = 2

[[category]]
name = "Ошибки КАСУ — Сервер"
priority = 5          # необязательно, по умолчанию 0
weight = 1            # необязательно, по умолчанию 1
include = ["сервер"]
exclude = ["отчет", "отчёт"]
```

В JSON (когда конфиг уезжает в интерфейс) поле называется `categories`; в TOML
массив таблиц называется `[[category]]`. Для совместимости при разборе принимаются
оба имени — за это отвечает `#[serde(alias = "category")]`. Если перепутать, во
вкладке «Категории» появится ошибка о конфиге без списка категорий.

### Порядок поиска

1. `categories.toml` рядом с exe — портативная версия;
2. `categories.toml` в текущей папке — запуск из репозитория;
3. рядом с exe, если папка доступна для записи (проба создаётся и удаляется);
4. пользовательская папка настроек.

Пункт 3 нужен, чтобы portable-версия оставалась самодостаточной, а пункт 4 — чтобы
работали установленные сборки, где каталог программы защищён от записи
(`Program Files`, `/usr/bin`).

Путь вычисляется один раз при старте GUI и хранится в `AppState::config_path`.

### Встроенный и пользовательский стандарт

- **Встроенный** — `categories.toml` в корне репозитория, попадает в бинарь через
  `include_str!` при компиляции. Правка файла требует пересборки.
- **Пользовательский** — `categories.default.toml` рядом с рабочим конфигом.
  Создаётся кнопкой «Сделать стандартными». Если файл есть, «Сбросить к
  стандартным» восстанавливает именно его, иначе — встроенный набор.
  В ответе команды `reset_categories` приходит поле `source`: `"user"` или `"factory"`.

## Excel-отчёт

`save_report` создаёт книгу из двух листов.

**«Данные»** — исходные колонки плюс колонка «Категория», заголовки жирным,
закреплена первая строка. Ширины колонок рассчитываются по заголовкам:
`autofit()` в `rust_xlsxwriter` считает ширины в момент вызова, а вызывается он до
записи строк данных. Для длинных описаний это скорее плюс, но знать об этом стоит.

**«Статистика»** — таблица «Категория / Количество / Доля» по убыванию, строка
«Итого», две встроенные диаграммы: кольцевая (доли категорий) и гистограмма
(топ-10). Диаграммы настоящие объекты Excel, а не картинки, — они перестраиваются
при правке чисел.

## GUI: бэкенд

### Состояние

```rust
pub struct AppState {
    config: Mutex<CategoriesConfig>,            // текущие правила
    config_path: PathBuf,                       // куда сохранять правила
    default_config_path: PathBuf,               // categories.default.toml
    last_results: Mutex<Vec<ClassificationResult>>, // кэш классификации
}
```

`last_results` наполняется в `classify_files` и используется командами
`get_classified_page` и `save_report_file`.

### Команды

| Команда | Аргументы (JS → Rust) | Возвращает | Что делает |
|---|---|---|---|
| `pick_input_files` | — | `string[]` | Диалог выбора xlsx (несколько файлов) |
| `pick_save_path` | `defaultName` → `default_name` | `string` | Диалог сохранения. В интерфейсе не используется: сохранение идёт через JS-диалог плагина |
| `classify_files` | `paths` | `FileSummary[]` | Классифицирует файлы, пишет прогресс, обновляет кэш |
| `get_classified_page` | `fileIndex`, `page`, `pageSize`, `search`, `categoryFilter` | `DataPageResponse` | Страница данных с фильтрами |
| `save_report_file` | `inputPath`, `outputPath` | `string` | Сохраняет отчёт; берёт результат из кэша, если файл уже классифицирован |
| `get_categories` | — | `CategoriesConfig` | Текущие правила |
| `set_categories` | `configToml` | — | Валидирует и сохраняет правила в файл и в состояние |
| `set_default_categories` | `configToml` | — | Запоминает правила как пользовательский стандарт |
| `reset_categories` | — | `{ config, source }` | Возвращает правила к стандарту |

Имена аргументов: в JS — camelCase, в Rust — snake_case, преобразование делает
Tauri. Параметры `State<'_, AppState>` и `tauri::WebviewWindow` в JS не передаются.

### События

`classify_files` эмитит событие `classify-progress` в окно:

```json
{ "processed": 2, "total": 5, "current_file": "tickets.xlsx" }
```

Фронтенд слушает его в `upload.ts` и двигает прогресс-бар.

### Тяжёлые операции

Чтение и классификация файлов выполняются в `tauri::async_runtime::spawn_blocking`,
чтобы не блокировать поток обработки событий Tauri: на 30 тысячах строк это
заметное время. Команды, работающие только с состоянием (`get_categories`,
`get_classified_page`), синхронные.

### Разрешения

`src-tauri/capabilities/default.json` выдаёт окну `main` права `core:default`
(базовые, включая события) и `dialog:default` (диалоги выбора файлов). Без этого
`invoke` к плагину диалогов падает, а обработчик молча ничего не делает.

### Кэш результатов и его последствия

`save_report_file` ищет результат по **имени файла** (`source_name`), а не по
полному пути. Если в сессии классифицировались два файла с одинаковым именем из
разных папок, для отчёта возьмётся первый. Кэш также означает, что после правки
правил старый результат сохранится в отчёт без переклассификации — нужно нажать
«Классифицировать» заново.

## GUI: фронтенд

Сборка — Vite. В dev-режиме Tauri подключается к `http://localhost:1420`
(`devUrl` в `tauri.conf.json`), в релизе фронтенд вшивается из `ui/dist`.
Фреймворка нет: модули на TypeScript строят DOM напрямую, Chart.js подтягивается
динамическим импортом только при построении графиков.

| Модуль | Ответственность |
|---|---|
| `main.ts` | Разметка всех вкладок, переключение, инициализация модулей |
| `api.ts` | Типы и обёртки `invoke` — единственное место, знающее имена команд |
| `upload.ts` | Выбор файлов, drag-and-drop, прогресс, классификация, сохранение отчёта |
| `dataViewer.ts` | Таблица данных: пагинация, поиск, фильтр категорий, скрытие столбцов |
| `charts.ts` | Кольцевая диаграмма, гистограмма и сводная таблица |
| `editor.ts` | Редактор категорий и сериализация правил обратно в TOML |
| `style.css` | Все стили, тёмных тем нет |

Распределение работы по вкладке «Данные»: **фильтрация и пагинация — на бэкенде**
(в файле может быть десятки тысяч строк, целиком их в интерфейс отдавать нельзя),
а **скрытие столбцов — на клиенте**, потому что оно не влияет на выборку.

Вкладка «Данные» перезагружается при входе на неё и после каждой классификации;
графики пересчитываются из сводок, полученных от `classify_files`.

## Тесты

- `src/lib.rs`, модуль `tests` — юнит-тесты определения доступности записи.
- `tests/defaults.rs` — встроенный стандарт: валидность, наличие настроенных слов,
  приоритет «Нефтебазы», совпадение с рабочим конфигом (если тот есть),
  имя файла конфига.

Запуск: `cargo test`. Тесты бэкенда GUI и фронтенда не покрыты.

## Известные ограничения

- **Только первое совпадение по файлу:** обрабатывается первый лист книги, колонка
  строго с именем «Описание».
- **Одна книга — один отчёт с диаграммами:** при нескольких загруженных файлах
  отчёт сохраняется для каждого отдельно, сводный отчёт по всем файлам не строится
  (графики в интерфейсе при этом агрегируются).
- **Сопоставление по подстроке** даёт ложные срабатывания на коротких словах
  (`пк`, `фн`) — их лучше держать с уточнением.
- **Категории не переупорядочиваются в интерфейсе:** ничья разрешается порядком
  объявления, а изменить порядок можно только правкой TOML.
- **Нет devtools в релизе** и нет отдельного лог-файла — диагностика GUI ограничена
  сообщениями в интерфейсе.
- **Windows-сборка без консоли только в release:** в debug консоль остаётся
  намеренно, туда пишутся логи.
